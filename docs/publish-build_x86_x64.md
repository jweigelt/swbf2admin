This document explains the **`Release-x86-x64`** publish profile
([`SWBF2Admin/Properties/PublishProfiles/Release-x86-x64.pubxml`](../SWBF2Admin/Properties/PublishProfiles/Release-x86-x64.pubxml)),

## 1. What the release folder looks like

Running the profile produces this layout (written to `build_x86_x64\` in the
repo root):

```
build_x86_x64\
|   SWBF2Admin.exe                  <- the app (framework-dependent, single-file, win-x64)
|   SWBF2Admin.sqlite               <- empty database seed
|   gametypes_flags_calculator.htm
|   Reset WebAdmin users.bat
|   LICENSE
|   readme.md
|
+---cfg\
|   \---dyncmd\                     <- Lua dynamic commands (bandwidth, boom, stats, ...)
|
+---web\                            <- WebAdmin templates (frame.htm, mods.htm, ...)
|   \---res\                        <- WebAdmin static assets (js, css, images)
|
+---licenses\                       <- third-party license texts
|
\---server\
	|   DllLoader_32.exe            <- injector for 32-bit game (GameSpy/Galaxy)
	|   DllLoader_64.exe            <- injector for 64-bit game (Aspyr)
	|   RconServer_32.dll          <- native RCON module (32-bit) *
	|   RconServer_64.dll          <- native RCON module (64-bit) *
	\---settings\
			ServerSettings.cfg
			ServerRotation.cfg

* RconServer_32/64.dll are built separately (native C++/CMake). See section 6.
```

## 2. Where every file comes from

| Release path | Source in the repo | Produced by |
| --- | --- | --- |
| `SWBF2Admin.exe` | `SWBF2Admin/SWBF2Admin.csproj` | `dotnet publish` (this profile) |
| `SWBF2Admin.sqlite` | `DebugFiles/SWBF2Admin.sqlite` | copy |
| `gametypes_flags_calculator.htm` | `DebugFiles/gametypes_flags_calculator.htm` | copy |
| `Reset WebAdmin users.bat` | `DebugFiles/Reset WebAdmin users.bat` | copy |
| `LICENSE`, `readme.md` | repo root | copy |
| `cfg\**` | `DebugFiles/cfg/**` | copy |
| `web\**` (incl. `res\**`) | `DebugFiles/web/**` | copy |
| `licenses\**` | `licenses/**` (repo root) | copy |
| `server\DllLoader_32.exe` | `DllLoader/DllLoader.csproj` (win-x86) | `dotnet publish`, then renamed |
| `server\DllLoader_64.exe` | `DllLoader/DllLoader.csproj` (win-x64) | `dotnet publish`, then renamed |
| `server\RconServer_32.dll` | `rconserver-galaxy/` (CMake, 32-bit) | native build (manual) |
| `server\RconServer_64.dll` | `rconserver-aspyr/` (CMake, 64-bit) | native build (manual) |
| `server\settings\ServerSettings.cfg` | `SWBF2Admin/Resources/template/ServerSettings.cfg` | copy |
| `server\settings\ServerRotation.cfg` | *(no repo source)* | generated by the profile |

> **Why `DebugFiles`?** At runtime the app resolves its web templates from
> `./web` (see `Constants.WEB_DIR_ROOT`) and its config from `./cfg`, relative to
> the executable. `DebugFiles` is the canonical copy of those runtime assets, so
> the release simply copies the whole tree next to the published `.exe`.

## 3. How to run the profile

### Recommended: from the command line
This is the most reliable way and is what you should use:
```powershell
dotnet publish SWBF2Admin\SWBF2Admin.csproj -p:PublishProfile=Release-x86-x64
```

If you have already built the native RconServer DLLs somewhere else, point the
profile at them:
```powershell
dotnet publish SWBF2Admin\SWBF2Admin.csproj -p:PublishProfile=Release-x86-x64 `
  -p:RconServer32Dll=C:\builds\RconServer_32.dll `
  -p:RconServer64Dll=C:\builds\RconServer_64.dll
```

The assembled folder is written to `build_x86_x64\` in the repo root.

> If the two `RconServer_*.dll` files are missing, the publish still **succeeds**
> but prints a warning for each; you then drop the DLLs into `server\` yourself.

### From Visual Studio (and the UI caveat)
1. Right-click the **SWBF2Admin** project ? **Publish...**
2. Select the **Release-x86-x64** profile.
3. Click **Publish**.

> **Heads-up about the Publish UI.** When you open the publish dialog, Visual
> Studio **re-serializes the top `<PropertyGroup>` of the `.pubxml`** based on what
> its settings screen shows. In the past this rewrote `PublishDir` and turned the
> repo-relative paths into machine-specific **absolute** paths (e.g.
> `C:\Users\...\swbf2admin\..\`, which pointed *outside* the repo and broke the
> DllLoader build). To make the profile UI-proof, all the custom/derived paths
> (`RepoRoot`, `RconServer32Dll`, `RconServer64Dll`) now live **inside the
> `<Target>`** and `RepoRoot` is computed at build time from
> `$(MSBuildProjectDirectory)`. The UI only round-trips the handful of well-known
> publish properties at the top, so it can no longer corrupt the assembly logic.
>
> If a UI publish ever misbehaves, just use the command line above — it never
> rewrites the profile.

## 4. How the profile works, property by property

The profile is a normal MSBuild `.pubxml`. The top `<PropertyGroup>` holds the
standard publish settings (the only things the Visual Studio Publish UI
round-trips); a second custom `<Target>` holds the derived paths and assembles
the folder afterwards.

| Property | Value | Why |
| --- | --- | --- |
| `Configuration` | `Release` | Optimized build. |
| `Platform` / `RuntimeIdentifier` | `x64` / `win-x64` | Reference exe is 64-bit. |
| `SelfContained` | `false` | Framework-dependent: the target server already has the .NET SDK/runtime installed, so the runtime is **not** bundled. Keeps the exe small. |
| `PublishSingleFile` | `true` | One `SWBF2Admin.exe` instead of many DLLs. |
| `PublishReadyToRun` | `true` | Faster startup (AOT-precompiled). |
| `DebugType` / `DebugSymbols` | `none` / `false` | Do not emit/ship a `.pdb` (the reference release has none). |
| `PublishDir` | `..\build_x86_x64\` | Output location (relative to the project dir, so it lands in `build_x86_x64\` at the repo root). |
| `RepoRoot` *(set inside the target)* | `$([MSBuild]::NormalizeDirectory('$(MSBuildProjectDirectory)\..'))` | Absolute repo root, anchored to the project dir. **Important:** paths in a `.pubxml` resolve relative to the *project file* (`SWBF2Admin\`), **not** the profile file — so the repo root is one level up. It's defined **inside the `<Target>`** (not the top property group) and made absolute so (a) the Publish UI can't overwrite it and (b) the `<Exec>` sub-processes resolve it correctly regardless of their working directory. |
| `RconServer32Dll` / `RconServer64Dll` *(set inside the target)* | `$(RepoRoot)rconserver-*/out/RconServer_*.dll` | Default locations of the pre-built native DLLs; override on the command line. Kept inside the `<Target>` so the Publish UI can't rewrite them to absolute machine paths. |

> **Framework-dependent, not self-contained.** Both `SWBF2Admin.exe` and the two
> `DllLoader` executables are published **framework-dependent** (`SelfContained=false`),
> because the machines that run them have the .NET runtime installed. This keeps
> the binaries small and matches the `x86`/`x64` DllLoader publish profiles in
> `DllLoader\Properties\PublishProfiles\`. Trimming is left **off** — the app uses
> reflection + XML serialization for config loading, which trimming can break.

## 5. How the assembly target works

The `AssembleReleaseFolder` target runs **`AfterTargets="Publish"`** — i.e. right
after `SWBF2Admin.exe` lands in `PublishDir`. It performs five stages:

1. **DllLoader (32 + 64-bit).** Runs `dotnet publish` on `DllLoader.csproj` twice
   (once per RID) via `<Exec>`, then copies each resulting `DllLoader.exe` into
   `server\` as `DllLoader_32.exe` / `DllLoader_64.exe`. The `dotnet publish`
   commands replicate the settings from the DllLoader `x86`/`x64` publish profiles
   (`--self-contained false -p:PublishSingleFile=true -p:PublishReadyToRun=true`).
   - `<Exec>` is used instead of the MSBuild `<MSBuild>` task on purpose: each RID
	 needs its **own restore** and must **not inherit** this profile's
	 `PublishProfile` property. A separate `dotnet publish` process gives clean
	 isolation (a nested `<MSBuild>` call shares `obj\` and the global properties,
	 which causes `NETSDK1047` and `NETSDK1198`).
2. **Runtime assets.** Copies the whole `DebugFiles\**` tree into the release
   root, preserving structure (this produces `cfg\`, `web\`, `web\res\`, and the
   loose root files like `SWBF2Admin.sqlite`).
3. **Licenses + docs.** Copies `licenses\**` into `licenses\`, plus `LICENSE`
   and `readme.md` into the root.
4. **Server settings.** Copies `ServerSettings.cfg` from the template folder and
   writes a `ServerRotation.cfg` (there is no source file for the latter in the
   repo, so a minimal one matching the reference is generated).
5. **Native RconServer DLLs.** Copies `RconServer_32.dll` / `RconServer_64.dll`
   **if they exist** at the configured paths; otherwise emits a `<Warning>` with
   instructions. The publish is never failed by their absence.

Because everything lives inside the `.pubxml`, the release logic is
self-contained and does **not** pollute the main `SWBF2Admin.csproj`.

## 6. Building the native RconServer DLLs

`RconServer_32.dll` and `RconServer_64.dll` are **native C++** modules and are
**not** part of the .NET solution, so MSBuild cannot build them. They come from
two CMake projects:

| DLL | Project folder | Target game |
| --- | --- | --- |
| `RconServer_32.dll` | `rconserver-galaxy/` | 32-bit (GameSpy/Galaxy) `BattlefrontII.exe` |
| `RconServer_64.dll` | `rconserver-aspyr/` | 64-bit (Aspyr) `Battlefront2.dll` |

To build one (example, from a *Developer Command Prompt* with CMake + a C++
toolchain installed):

```powershell
cd rconserver-galaxy
cmake -B out -A Win32           # 32-bit; use -A x64 for rconserver-aspyr
cmake --build out --config Release
```

Then either:
- copy the resulting `RconServer_32.dll` to `rconserver-galaxy\out\` (the default
  path the profile looks in), **or**
- pass its path with `-p:RconServer32Dll=<path>` when publishing.

Do the same for `rconserver-aspyr` ? `RconServer_64.dll`.

## 7. How to author a profile like this from scratch

If you ever need to recreate this (or make a similar one for another layout),
here is the recipe:

1. **Generate a starter profile.** In Visual Studio, *Publish* the project once
   to a folder target. This creates
   `Properties\PublishProfiles\<Name>.pubxml` with the basic
   `Configuration` / `Platform` / `PublishDir` properties.

2. **Match the reference binary.** Decide self-contained vs. framework-dependent:
   - If the target machine has the .NET runtime/SDK installed (as ours does),
     use `SelfContained=false` + `PublishSingleFile=true` to keep the exe small.
   - If it might not, use `SelfContained=true`; add `EnableCompressionInSingleFile=true`
     and `IncludeNativeLibrariesForSelfExtract=true` to shrink the bundled runtime.
   - Add `DebugType=none` + `DebugSymbols=false` if no `.pdb` should ship.
   - Leave `PublishTrimmed=false` for apps that use reflection/serialization.

3. **Point the output somewhere safe.** Set `<PublishDir>` to a `_out` folder so
   you never clobber the thing you are trying to replicate. **Watch the path
   anchor:** relative paths in a `.pubxml` resolve against the *project file*,
   **not** the profile file. Since the project lives one level under the repo root
   (`swbf2admin\SWBF2Admin\`), `..\` reaches the repo root. Anchor shared paths to
   `$(MSBuildProjectDirectory)` and make them absolute so any `<Exec>` sub-process
   resolves them correctly regardless of its working directory.

4. **List every file in the reference and find its source.** Build a table like
   section 2. Group files by origin (project output vs. static asset vs. root doc
   vs. externally-built binary).

5. **Add an `AfterTargets="Publish"` target** to copy those groups:
   - Use `<ItemGroup>` + `<Copy>` with the
	 `@(Items->'$(Dest)%(RecursiveDir)%(Filename)%(Extension)')` transform to copy
	 whole trees while preserving structure.
   - Use `<Copy DestinationFolder="...">` for a handful of loose files.
   - Use `<WriteLinesToFile>` for files that have no source in the repo.

6. **Handle secondary build outputs** (like `DllLoader`) with `<Exec>` calls to
   `dotnet publish`, then `<Copy>`/rename. Prefer `<Exec>` over the `<MSBuild>`
   task when the sub-project needs its own restore/RID and must not inherit the
   parent's publish properties.

7. **Handle externally-built artifacts gracefully.** For anything MSBuild can't
   build (native code, etc.), copy it `Condition="Exists(...)"` and emit a
   `<Warning>` with build instructions when it's missing — so the publish never
   hard-fails on an optional binary.

8. **Escape correctly.** Inside `.pubxml`:
   - XML comments **cannot** contain `--` (so avoid `----`/`====` dividers).
   - Escape `<` / `>` as `&lt;` / `&gt;` and quotes inside `Command="..."` as
	 `&quot;`.

9. **Test end-to-end.** Delete the output folder, run the publish, and diff the
   result against the reference (`Get-ChildItem -Recurse`) until the structure and
   file sizes line up.
